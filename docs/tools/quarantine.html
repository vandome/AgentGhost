What it is for

file_system's download operation already reached a .onion URL over Tor, but the file landed in the normal sandbox. That sandbox is bind-mounted read-write into the container that runs execute (which has Tor egress), it is served by /api/download, shown by the web workspace, and copied into the daily snapshots. Nothing marked the file as untrusted. A dark-web file is research material, not a workspace file, so it now goes somewhere none of those can reach.

Where a file goes

  • The quarantine directory is <GHOST_HOME>/quarantine/, a sibling of sandbox/. The sandbox mount, /api/download (which resolves under the sandbox and checks containment), the workspace console and the snapshot (which copies system/ and sandbox/) never see it. The model cannot choose a path: a path passed with an onion URL is ignored.
  • Name and mode: the file is stored as <sha256>.bin, mode 0600, no execute bit. The same content twice is kept once.
  • The sidecar <sha256>.json records the source URL, the final URL after redirects, the time, size, SHA-256 and MD5, the type read from the file's first bytes (never from its extension), whether that type is executable (PE, ELF, Mach-O, legacy Office/MSI, a shebang script), the request id, and whether it has been inspected.

The download

  • Routed automatically: file_system(operation='download', url='http://….onion/…'). A clearnet URL takes the normal path, unchanged.
  • Over Tor only, with socks5h, so the onion name is resolved inside Tor and never by this machine's resolver. The shared SSRF check runs on every hop.
  • Redirects are followed up to 5 hops, and every hop must stay on a dark-web host. A redirect to the clearnet is refused rather than followed: that would change what the file is.
  • Caps: 50 MB per file (the Content-Length and the streamed bytes are both checked), 2 GB for the whole quarantine, and a 90-second wall clock on the transfer (curl's stream timeout is only a low-speed limit, so a host trickling bytes would otherwise hold the turn). A failed or interrupted download leaves nothing behind; a part-file a crash left is purged after an hour.
  • The result names the id and type, says the file cannot be read, run, opened or served, flags an executable type, and points at quarantine_inspect.

Inspection

file_system(operation='quarantine_inspect', quarantine_id=…) produces a report inside a separate container, not the sandbox: docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges --memory 512m --pids-limit 64 --user 65534:65534, with the one file mounted read-only at /q/file and a 60-second limit. It reports the file type, size, SHA-256, a head of strings, the first pages of a PDF as text, and for an archive a listing (7z l), never an extraction. The report is defused (role-forging tags made inert) and labelled as untrusted content before the model reads it.

Retention, access, operations

  • 7 days. Files older than that are purged on every quarantine access and once at boot; a blob without a sidecar or a sidecar without a blob is removed too.
  • Owner only. Only the owner's own turn, the wake-up of a job the owner started, or an operator probe may touch the quarantine. A member's request, a scheduled or background turn and self-play (which replays owner turns verbatim) are refused before anything is fetched, listed, inspected or deleted.
  • Only Tor hidden services. .i2p is not recognised: the agent runs no i2p proxy, so such a download could only fail.
  • Encoded hosts. libcurl percent-decodes a host and folds Unicode dots (． 。 ｡) and fullwidth letters to ASCII before it connects, and it reads 0177.0.0.1 or 0x7f000001 as 127.0.0.1. So …%2eonion and abc．ｏｎｉｏｎ are onions to Tor even though a URL parser sees neither. Both the onion check and the shared SSRF guard now judge one canonical host (helpers.canonical_host: decoded, IDNA-folded, lowercased), the guard refuses any percent sign in the host part, and it refuses numeric host forms that are not a plain address. Before this, 127%2e0%2e0%2e1 and 0177.0.0.1 reached the loopback.
  • Known open path (accepted by the operator, 2026-10-11): the sandbox's own Tor egress lets a shell command in execute fetch an onion URL directly into the workspace. The quarantine protects files fetched by the download tool; it does not police the shell.
  • The mirror rule on the clearnet path: a clearnet download whose redirect lands on a .onion host is refused rather than followed, so no dark-web file can reach the workspace by way of a redirect.
  • quarantine_list shows the files with age and purge time; quarantine_delete takes the id or a unique prefix of at least 8 characters.
  • All file types are allowed (operator decision, 2026-10-11). The author recommended refusing image and video types from dark-web hosts on legal-risk grounds; the switch GHOST_QUARANTINE_REFUSE_MEDIA=1 turns that refusal on. Nothing in the quarantine is ever previewed, rendered, thumbnailed or served.
