How it works

How it improves itself

Two separate things: a check that runs on every answer, and a set of background passes that only run when you've left it alone. Since October 2026 the only thing that changes how it answers is a rule you approved.

To be clear about what this isn't. None of this retrains the language model. The model file never changes. What changes is what Ghost remembers and the rules you have approved. Everything happens on your machine.
Looking for how it learns from you? The whole loop — your 👎, the replays while you're away, the rule it proposes, your decision, and the regression tests that keep a fix fixed — has its own page with a worked example: The learning loop.

Part one: checking its own answers

The failure this exists to catch is specific and common: a model announces "I've created the file and it works" when nothing ran, or answers a subtly different question than the one you asked. It reads confidently either way, which is what makes it dangerous.

So before an answer is final, a second pass reads it against the evidence the tools actually produced.

  1. The evidence is collected

    What the tools returned this turn — command output, file contents, what the browser saw. Not the model's description of them; the actual results.

  2. Two questions, in this order

    First: does this answer the question that was asked? Second: is it supported by the evidence? Alignment comes first deliberately — "you asked for code and got a number" is a worse failure than a wrong number, and a check that only looks at correctness misses it entirely.

  3. A verdict, with a confidence

    Confirmed, or refused. A cheap local judge does the first pass; if it refuses, the main model re-examines the case, and its verdict wins. That second look exists because the cheap judge refuses more often than it should.

  4. If refused with high confidence — repair

    Ghost gets a bounded number of attempts (one by default) to fix the answer with the critique in hand, rather than shipping something it just failed. Error messages and aborts are never "repaired". The launcher sets GHOST_CRITIC_ASYNC=1, which skips this repair: every answer is sent first and checked afterwards, and a confident refusal becomes a correction at the top of your next reply. Since 2026-10-10 (§4NF) that correction is not shown to you (2 of the last 3 shown corrections were false; the switch that showed them was removed on 2026-10-11, §4NM); the verdict is still recorded and can start a replay in the learning loop.

  5. Whatever happens is recorded

    The verdict is stored with the turn. A refused or doubtful answer of yours can be put on the list for the learning loop to replay — but nothing is ever adopted on the self-check's word, because measured against the truth it is wrong too often (it confirmed an invented "all systems green" two times out of two). Ghost no longer writes lessons for itself: the producers that did (reflection, post-mortems, distillation, dream consolidation) were removed on 2026-10-11 (§4NM).

Streaming answers are checked late

If the reply streams word by word, the text has already reached you by the time the check finishes. Blocking would buy nothing. So the check runs in the background and, if it refuses, you get a correction notice at the top of the next reply. It is after the fact — and since 2026-10-10 (§4NF) the correction is not shown to you at all: 2 of the last 3 shown corrections were false, and the switch that showed them was removed on 2026-10-11 (§4NM). The verdict is still recorded and can start a replay in the learning loop.

When you correct it yourself

Telling Ghost it got something wrong is a much stronger signal than anything it can generate on its own, and it's treated that way: the turn gets marked as failed. It needs both a recognisable correction phrase and genuine overlap with the previous message, so an ordinary follow-up question isn't mistaken for a correction. While you're away, the main model also reads your next message after each answer, in a short background check, and decides whether it showed the answer missed. Your 👎 and these corrections are what the learning loop starts from: they are the only signals that can lead to a regression test. The self-check's doubts or a run of failed tool calls can also start a replay, but never a test.

Part two: what it does while you're away

A background loop — the idle scheduler (formerly called the biological watchdog) — wakes up periodically and checks whether it's allowed to do anything. Two rules govern all of it:

  • It never interrupts you. If a request is in flight — even paused between model calls — every phase is skipped.
  • Each phase needs both idle time and a cooldown. "It's been quiet for an hour" isn't enough if that phase already ran twenty minutes ago.

So on a busy day, almost none of this runs. That's intended.

One mechanism is easy to misread. Most phases only run while you've been idle between fifteen and sixty minutes. Past an hour that window rolls over and opens again, so during a long absence each phase gets another chance after its cooldown. Until October 2026 only self-play finishing re-opened the window, which meant --no-self-play quietly stopped almost everything else too; the window now rolls on its own (§4LF), and the roll never touches the clock that records when you were last active.

If you use --bio-time-scale to exercise these loops quickly: it now divides the phase cooldowns and the loop's own tick interval as well as the idle windows. Until 2026-08-08 it only compressed the windows — the cooldowns kept their real durations, so a phase with a three-hour cooldown could fire at most once no matter how many accelerated epochs a run claimed to cover. The helper meant to scale them existed and had a passing unit test, but nothing ever called it. Any measurement taken with this flag before that date covers roughly one epoch per phase, whatever it says.

There is a floor on how far you can compress time

Accelerating the clock only works while the compressed window stays wider than the work. The gates shrink when you raise the scale; the work doesn't. A dream is a real model call and takes something like a minute whether the scale is 1 or 60.

At --bio-time-scale 60 the window for the middle phases is 45 seconds — narrower than a single dream. What was actually observed, tick by tick:

idle 1..10s   nothing eligible yet
idle ~11s     dream starts — and runs for ~60 real seconds
idle ~71s     the 15–60s window has already closed
              self-play (no upper bound) fires and resets the idle clock
idle 1..10s   …and round again, forever

The middle of the window is never sampled, so calibration, the tidy pass, both narrative consolidations, stale-question surfacing and project auto-advance can never run — and they report zero firings, which reads exactly like "we measured them and they did nothing."

Practical rule: keep the scale at 20 or below (a window of at least ~2 minutes). The agent now warns loudly at boot if the scale you chose makes the window narrower than the work, and names the phases that would silently never fire. Every ablation number recorded before 2026-08-09 measured dreaming and self-play only.

  1. After ~2 minutes — file away what just happened

    Things noted during the conversation are sitting in a queue. This pass works through them and decides what's worth keeping, then writes it into long-term memory. Until this runs, something you just mentioned may not be findable.

  2. After ~10 minutes — maintenance

    The log calls this phase maintenance (it was once called dream, and the code module is still core/dream.py); its console line is tagged Idle Maintenance. It writes project digests, backfills the project manifests, purges the forget archive, prunes and merges the knowledge graph, archives old trajectories and takes the daily verified snapshot of the stores — about every six hours on a quiet day. The REM consolidation that used to turn memories into lessons here was removed on 2026-10-11 (§4NM).

    It skips itself when there's nothing new, and backs off further each time it skips — so a quiet afternoon doesn't produce a log full of "nothing to do".

  3. After ~15 minutes — keep its own records

    Ghost updates its running first-person account of what it's been doing, and its record of what changed in your files. Reviewing failed turns (reflection) used to write lessons here too; measured on real turns, those lessons reached the turn they were meant for 18% of the time and changed the reply in 3 of 20, and it was removed on 2026-10-11 (§4NM).

  4. Every hour or so — refit the confidence calibration

    The calibration tracker pairs each turn's confidence with how the turn actually ended and re-fits the weights, so the least confident answers are the ones routed to the deeper check. Skipped when nothing new has been recorded. (The plan-scorer retrain, the request router and automatic skill extraction that used to run in this slot were removed on 2026-10-11, §4NM.)

  5. After ~1 hour — replay your failures, and run your tests

    Ghost picks a recent turn of yours that went wrong — you gave it a 👎, or your next message showed the reply missed — and asks the same question again as a labelled test, with and without a candidate rule. Ghost then tells you the rule and what happened with and without it: Candidate rule 3 — say “show rule 3” to read it, “learn rule 3” to adopt it. Nothing is learnt until you say so; “show all rules” lists them and “forget rule N” removes one (after you confirm).

    The same evidence also becomes regression tests (§4NE). Ghost drafts one — the question, what a right answer must contain, and checks a program can run — and asks you: “keep test 4”, “edit test 4: it must name the vendor's page”, or “forget test 4” (“show regression tests” lists them). Kept tests are re-asked after every update to Ghost and once a day, and a failing one is reported to you. A candidate rule is also run against your kept tests, so its proposal says whether it breaks any of them. See core.regression.

    With no recent failure and no test due, nothing runs — the Idle Cycle console line then ends — failure replay: nothing to do (no owner failure to replay, no test due); when the slot did run it ends with what it did. Invented practice problems were removed on 2026-10-11 (§4NM).

Times are how long you've been quiet. Each phase also has its own cooldown between runs.

One more that is off by default

It stays off unless you turn it on.

Advancing projects on its own
When idle, push one active project forward by one step without being asked. Runs on hard per-project budgets with human gates. Turn on with --autoadvance-idle.

What all of this is actually reading

Every one of those passes reads the same thing: a trajectory — one JSON line per turn recording what was asked, which tools ran in what order, what came back, and how it ended. They're written append-only to $GHOST_HOME/system/trajectories/, redacted on the way out, and if the write fails the turn carries on regardless. A logging failure must never break a user request.

That one log was built to feed several consumers, each asking a different question of it. In October 2026 each one was measured on real turns; most turned out not to help and were removed on 2026-10-11 (§4NM):

Is a kept regression test still passing?A pass/fail per test, reported to you on failure.on — core.regression
What did you do while I was away? Which experiment arms ran?Ledger reads for introspect.on

What used to be here

Until 2026-10-11 this page also described automatic skill extraction, the rules that made a self-written lesson count, two small logistic-regression models Ghost trained on its own turns (a plan scorer and a request router), and an offline prompt optimizer (GEPA) with its A/B ship gate, live judge and self-launching loop. Each was measured on real turns in October 2026 and found not to change an answer for the better; all of them were removed (§4NM). What remains of the optimizer is the small loader in optim/ that renders tool descriptions from their signatures — every prompt Ghost uses is hand-written. The lessons those systems taught about measurement are kept below and in the project journal.

Seeing what actually happened

All of this is invisible by design — routine background work doesn't interrupt your conversation. To see it, ask.

"What did you do while I was away?"
Reads the background activity ledger — which passes ran, what came out of them, over whatever window you name.
"show all rules"
The rules you adopted, the ones waiting for you, and the forgotten ones — read from the store by Ghost itself, not recalled by the model.
"show regression tests"
Your kept and proposed tests, each with its last result.
"Is your learning actually working?"
Health telemetry for the learning loop itself: are your rules reaching prompts, is the regression suite running, is the confidence calibration fitting. This is the page to check when you suspect a subsystem has quietly stopped running.

The second failure mode: a verdict with no power behind it

Silence is the failure mode above. This is its twin, and it is harder to spot because it produces output: a measurement that reads like a result but could not have come out any other way.

Two of them were live until 2026-08-21, both on the instruments every keep/kill decision here rests on:

  • "no difference detected yet" on every randomized arm. True, and unfalsifiable. Measured across the whole live board, each arm's confidence interval was two to six times wider than the largest improvement the metric could physically make — failure_rate sat at 0.203 with a half-width of 0.367, so the rate would have had to fall below zero to be called. Five arms × two quality metrics reading "no difference" looks like evidence the features don't help. It was the instrument having no power. The report now says so, names the ceiling it cannot clear, and gives the sample size at which an improvement verdict first becomes possible.
  • "Brier beats the base-rate predictor" on the confidence model. The comparison used a 1e-6 tolerance, which makes any numerical wobble a victory. The live model beat the base rate by 0.00108 — and the 95% paired-bootstrap interval on that delta is [−0.00246, +0.00017], straddling zero. The verdict now follows the interval and reads "is INDISTINGUISHABLE from the base-rate predictor", with the interval shown beside it.

A third instrument was dead in the other direction. The arm-stamp coverage alarm exists so that a broken stamp can't hide, but its denominator was every user turn ever recorded — most of them from before the framework shipped — so a total stamp outage would have moved the headline from 16.8% to about 16.3%, under an "under half" warning that had been permanently on. It now reports a trailing window beside the lifetime figure, and the window is the one that raises the alarm.

The general rule this leaves behind: absence of evidence is evidence of absence only when the design could have found something. Any instrument that reports a null result should be able to tell you what it would have taken to see one.

What was done about it (October 2026, §4ND). At this agent's traffic no randomised arm could reach a verdict within a useful time, so every arm was disabled; the arms' estimator (PPI) and the risk governor were removed on 2026-10-11 (§4NM), and the arm machinery itself (core/experiments.py and introspect action='experiments') was removed on 2026-10-11 (§4NN). The confidence score is now used only as a ranking — the least confident 15% of answers get the deeper check — and no longer reported as a probability, because re-computed from raw data it was no better than guessing the base rate. The improvement signal that remains is the one that has power: your own verdict, through the learning loop and its regression tests.

The characteristic failure mode here is silence. A learning pass that has stopped running looks exactly like a learning pass with nothing to do — both produce no output. If you want to know whether this machinery is alive, check biological_watchdog_alive on the health endpoint (the key keeps its old name; it reports the idle scheduler) and ask for the activity ledger. Don't infer it from the absence of errors.

Turning parts of it off

Every phase has an off switch, mostly so you can measure whether it's earning its cost.

FlagTurns off
--no-dreamStore maintenance and the daily snapshot. Leaves the rest running.
--no-self-playThe learning loop's idle work: replaying your failures and running your regression tests. Leaves the rest running.
--no-trajectoriesRecording turns at all. This also stops the learning loop, since it has nothing to read.
--no-verifierThe self-check. Not recommended outside an experiment — see below.
--no-memoryEverything. Ghost becomes a plain chat wrapper.

The other direction — switches that are off unless you set them to 1 (environment variables, read on every use):

SwitchBrings back
GHOST_HYDRATION_JUDGEThe per-turn memory relevance judge.
GHOST_CODING_PRACTICECoding practice on a seed from one of your own failed coding requests.

The switches that used to sit beside these — GHOST_PRODUCER_LESSONS, GHOST_AUTO_SKILLS, GHOST_SKILL_PRUNE, GHOST_ROUTER, GHOST_FORESIGHT, GHOST_RISK_GOVERNOR, GHOST_GEPA_AUTONOMY, GHOST_BUS_VECTOR_TIER, GHOST_BUS_GRAPH_TIER, GHOST_BUS_EPISODIC_TIER, GHOST_BUS_SESSION_TIER, GHOST_DREAM_REPLAY, GHOST_EVOLVE, GHOST_COMPETENCE_PROMPT, GHOST_CONF_COMPETENCE, GHOST_VERIFIER_SHOW_OWNER — are gone with the code they switched (2026-10-11, §4NM). Why each went is on the learning loop page.

Why --no-verifier exists. When the check runs late (on a streamed answer), it can't change what you already read — its only payoff is cross-session: queueing a correction and marking the turn so the learning loop can replay it. That's a real benefit but not an obvious one, and it costs a full extra model call per turn. The flag exists so you can measure the difference rather than assume it.
